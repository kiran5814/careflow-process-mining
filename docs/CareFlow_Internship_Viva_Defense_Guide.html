2. Project Aim, Objectives & Problem Statement

The Hospital Operational Problem Statement

Emergency departments (ED) and acute inpatient units face compounding operational bottlenecks that lead to ambulance diversions, prolonged wait times, and regulatory financial penalties:

  1. The Radiology Paperwork Loopback (Rework): 39.8% of patients requiring diagnostic imaging experience repeat nursing triage because paper requisition slips lack physician counter-signatures or mandatory clinical indications. This adds +48 minutes of non-clinical dwell time and burns $142,400/year in nursing waste.
  2. Morning Surge Congestion (Temporal Bottleneck): Between 08:00 AM and 11:00 AM, patient arrivals spike to 102 patients/hour while single-technician staffing causes radiology queue delays to surge by +237% (54 min average wait).
  3. Inpatient ED Boarding Crisis: Admitted acute patients dwell in emergency treatment bays for an average of 4h 12m waiting for inpatient bed turnover (EVS cleaning), creating acute bed gridlock.
  4. Clinical Governance Violations: 5.1% of patients bypass nursing triage acuity assessment directly to doctor consultation without documented emergency fast-track justification.

Primary Objectives of the Project

  • Ingest & Validate: Clean and validate raw EHR event streams with 100% chronological integrity and zero data loss.
  • Process Discovery: Automatically discover the hospital's actual clinical pathway topology using Directly-Follows Graphs (DFG) rather than assumed static flowchart diagrams.
  • Root Cause & Explainable AI: Apply Ishikawa (Fishbone) frameworks, Six Sigma 5-Whys, and SHAP (SHapley Additive exPlanations) to quantify root causes of delays.
  • Regulatory Compliance: Actively audit CMS (Centers for Medicare & Medicaid Services) and The Joint Commission (TJC) hospital quality measures.
  • What-If ROI Optimization: Provide hospital leadership with an interactive simulation sandbox proving the financial and throughput ROI of proposed operational interventions.

5. Technology Stack & Framework Justifications ("Why Did You Use X?")

Technology Role Why It Was Chosen Over Alternatives
React 19 Frontend UI Framework Component-driven architecture allows isolating complex reactive states (e.g., live SVG token replay, countdown timers, and modal drawers) with fine-grained DOM updates without re-rendering the entire dashboard.
Vite 8 Frontend Build Engine & Bundler Replaced legacy Webpack. Vite uses native ES Modules during development for instant Hot Module Replacement (HMR < 50ms) and Rollup for production tree-shaking, resulting in a production build time of under 800ms.
Recharts 3 Data Visualization Built specifically for React and SVG. Unlike heavy canvas libraries, Recharts supports declarative SVG components (ResponsiveContainer, ComposedChart, Bar, Area, Radar, Funnel) that scale crisply across display resolutions and cleanly integrate with React state.
PM4Py (Python) Process Discovery Engine The open-source standard developed by Fraunhofer Institute and RWTH Aachen University. It provides native algorithms for Directly-Follows Graph (DFG) discovery, Alpha Miner, Inductive Miner, and IEEE alignment conformance checking.
dbt (Data Build Tool) In-Warehouse ELT Transformation Instead of error-prone Python transformation scripts, dbt enables modular SQL modeling with built-in data quality testing (not_null, unique), version-controlled dependency lineage DAGs, and separation into Staging views and Mart tables.
SQLite / PostgreSQL Relational Event Store Process mining logs require strict relational ACID guarantees for chronological event sequencing. Relational tables enable SQL window functions (LAG(), LEAD(), PARTITION BY) essential for transition duration calculations.
Vanilla CSS Design System Styling & Aesthetics Avoided Tailwind utility bloat. A curated Vanilla CSS design system provides native CSS custom properties (--bg-primary, --accent-cyan), dark-mode glassmorphism (backdrop-filter: blur), glowing SVG drop-shadows, and GPU-accelerated micro-animations.
Lucide React Medical & UI Iconography Lightweight, tree-shakeable SVG icons providing clean visual cues for clinical equipment, staffing roles, triage urgency, and emergency status codes.

7. IEEE Process Mining Quality Dimensions (Crucial Viva Topic)

When professors ask, "How did you evaluate your process discovery model?", cite the 4 IEEE Quality Dimensions:

  1. Process Fitness (F = 94.9%):
    • Definition: The ability of the discovered process model to replay the traces present in the event log without missing or remaining tokens.
    • Formula: F = 1 - (Missing Tokens + Remaining Tokens) / (Produced Tokens + Consumed Tokens)
    • Result: 94.9% of observed clinical paths replay flawlessly.
  2. Model Precision (P = 91.2%):
    • Definition: Measures how well the model avoids allowing unobserved, non-compliant behaviors (prevents "underfitting").
    • Result: The model strictly reflects healthcare pathways without creating unrealistic bypasses.
  3. Generalization (G = 88.5%):
    • Definition: Measures how well the model will accommodate future unseen patient traces that adhere to clinical logic.
  4. Simplicity (S = 96.0%):
    • Definition: Occam's razor principle — the model avoids unnecessary complex nodes or spaghetti transitions.

9. Top 15 Viva Questions & High-Scoring Answers

Q1: What is the difference between traditional Business Intelligence (BI) and Process Mining?
Answer: Traditional BI dashboards answer "What happened and how many?" using static aggregations (e.g., total patient count, average wait time). Process Mining uses timestamped event logs to answer "How did it happen, why did it deviate, and where did it loop?" by discovering the actual graph topology of patient journeys, revealing rework loops and sequence violations invisible in standard BI.
Q2: What is the Directly-Follows Graph (DFG) and how is it calculated?
Answer: A Directly-Follows Graph is a directed graph where nodes represent clinical activities and edges represent sequential execution. If activity B directly follows activity A within the same Case_ID, an edge (A → B) is recorded. The edge weight represents either transition frequency or average transition duration.
Q3: What is the biggest operational bottleneck you discovered in the hospital?
Answer: The Radiology Paperwork Loopback. 39.8% of patients (398 out of 1,000 cases) who arrived at the X-Ray suite were rejected by technologists and sent back to Triage because their physical paper requisition slips lacked doctor signatures or indication checkboxes. This added an average of +48 minutes of non-clinical waiting time and cost $142,400/year in wasted nursing labor.
Q4: How does your dbt pipeline transform the raw data?
Answer: The dbt project uses an ELT architecture:
  1. stg_ehr_events.sql standardizes column types, parses ISO-8601 timestamps, tags morning surge hours (08:00–11:00 AM), and calculates lag windows for transition deltas.
  2. fct_patient_journeys.sql aggregates case-level length of stay, detects triage bypass anomalies, and flags rework loops.
  3. mart_bottlenecks.sql, mart_sla_compliance.sql, and mart_resource_handovers.sql generate analytical summary tables for the dashboard.
Q5: What is SHAP and why did you use it in Root Cause Analysis?
Answer: SHAP (SHapley Additive exPlanations) is a game-theoretic approach to explainable machine learning. Rather than treating our XGBoost stay prediction model as a black box, SHAP decomposes each patient's predicted stay duration into additive minute contributions from a baseline of 110 minutes (e.g., Paperwork Loop adds +85m, Morning Surge adds +65m, High Acuity adds +40m, whereas low acuity subtracts -15m).
Q6: What is an Ishikawa (Fishbone) diagram and how does it apply here?
Answer: The Ishikawa diagram is a root cause analysis tool endorsed by The Joint Commission and Lean Six Sigma. It categorizes causes into 6 dimensions: Process, People, Technology, Policy, Environment, and Measurement. For example, in our project, the technology cause is the disconnected legacy PACS system, the policy cause is the wet-signature mandate, and the people cause is single-tech staffing.
Q7: What are the 5-Whys? Give an example from your project.
Answer: 5-Whys is an iterative root cause technique.
  1. Why did 398 patients return to Triage from X-Ray? Technologists rejected the requisition order.
  2. Why was it rejected? It lacked mandatory clinical indication checkboxes.
  3. Why were they missing? Nurses manually filled carbon-copy paper slips during intake surges.
  4. Why paper slips? The radiology ordering system was not integrated with the triage EHR module.
  5. Root Cause: Lack of Computerized Physician Order Entry (CPOE) with mandatory field hard-stops before order dispatch.
Q8: What is a CAPA register?
Answer: CAPA stands for Corrective and Preventive Action, an essential standard in ISO 9001 and Joint Commission healthcare governance. In CareFlow, our CAPA tracker (CAPA-2026-001 through CAPA-2026-005) assigns clinical leads, target completion dates, projected financial savings, and progress percentages to remediate identified root causes.
Q9: What is the ESI scale in Emergency Medicine?
Answer: The Emergency Severity Index (ESI) is a 5-level triage algorithm:
  • Level 1: Resuscitation (immediate life-saving intervention needed)
  • Level 2: Emergent (high risk, confused/lethargic, severe pain)
  • Level 3: Urgent (requires 2 or more diagnostic resources)
  • Level 4: Less Urgent (requires 1 resource, e.g., simple X-ray)
  • Level 5: Non-Urgent (requires 0 resources, e.g., prescription refill)
Q10: How does your What-If simulation calculate ROI?
Answer: It models eliminating paper requisition loopbacks through CPOE digitization:
  • Gross annual operational savings: $142,400 (nursing hours saved from 398 reworked cases).
  • Software implementation CAPEX: $24,000.
  • Net Year 1 ROI: ($142,400 - $24,000) / $24,000 * 100% = 394%, yielding a payback period of just 1.8 months.
Q11: What is Organizational / Social Network Mining in your project?
Answer: Implemented in ResourceHandoverNetwork.jsx, it analyzes the "handover of work" between clinical roles (Triage Nurse → Doctor → Radiologist → Inpatient Ward → EVS). It identifies communication friction and handoff delays (e.g., doctor-to-radiology handoffs stalling at 38.6 min due to physical paper requisitions).
Q12: Why did you use React 19 instead of a standard Python Streamlit app?
Answer: Streamlit reruns the entire Python script on every user interaction, making complex multi-view state management, SVG token animations (like our 100-tick DFG simulation), and sub-second interactive filters slow and clunky. React 19 provides component-level state isolation, virtual DOM diffing, and seamless client-side SVG manipulation with 60 FPS animations.
Q13: What is the Emergency Department Boarding crisis?
Answer: ED boarding occurs when an emergency patient is clinically admitted to the hospital but remains physically stuck dwelling in an acute emergency treatment bay because inpatient ward beds have not been cleaned by Environmental Services (EVS). In our hospital, boarding averages 4h 12m (252 min), exceeding the CMS ED-2b target of 240 minutes.
Q14: How did you test statistical significance in the Cohort Benchmark module?
Answer: We implemented two-sample Welch's t-tests and Mann-Whitney U tests to compare stay duration and loopback rates between cohorts (e.g., Morning Surge vs. Nominal Hours). The calculated p-value (p < 0.0001) proves that the 2h 26m delay in the morning is statistically significant and driven by structural bottlenecks rather than random variance.
